# SECURITY.md

What iTantra Message protects against, what it does not, and which claims are enforced by the
platform rather than asserted by the app.

Claims in this document are of two kinds, and they are marked:

- **[ENFORCED]** — checked by a command in this repository, or by the Android platform below
  the app. Cannot be silently broken by editing application code.
- **[BY DESIGN]** — true of the code as written, but nothing verifies it. A future change can
  break it and the build will still be green.

That distinction is the most important thing in this file.

---

## 1. The central guarantee: no network, enforced

**[ENFORCED]** The release APK does not declare `android.permission.INTERNET`.

```bash
bash scripts/check_offline.sh     # exit 0 = pass, 1 = fail, 2 = inconclusive, 3 = cannot verify
```

This is stronger than "we chose not to use the network". On Android the absence of the
permission is enforced *below the application*: the kernel refuses to let a process without it
create a socket. There is no API to call, no runtime permission to request, and no reflection
that gets around it, because the check is in the socket syscall path.

An APK without `INTERNET` cannot open a TCP or UDP connection even if code asks it to. This is
why the project is built this way, and why adding the permission would destroy the claim
silently — there is no way to add it "just for debugging" to a release build.

### 1.1 The check proves it can fail

A test that cannot fail proves nothing. So `check_offline.sh` also inspects the debug APK and
**requires that it does declare `INTERNET`**.

If both APKs lacked the permission, "pass" would mean nothing — `aapt` might be pointed at the
wrong file, or the permission might have been dropped from source entirely. By requiring debug
to be positive and release to be negative, the same `aapt` invocation is shown to detect the
permission in one build and not the other.

Exit codes are deliberately distinct. Treating *could not verify* as *passed* is how an offline
guarantee quietly stops being checked:

| exit | meaning |
|---|---|
| 0 | release has no `INTERNET`, debug has it — pass, check proven live |
| 1 | release declares `INTERNET` — fail, the central claim is broken |
| 2 | debug also lacks it — inconclusive, the check detected nothing |
| 3 | `aapt` or an APK missing — cannot verify |

Measured 2026-10-01 on the 0.1.0 build: release 1.28 MB, no `INTERNET`; debug 17.74 MB, has
it; exit 0.

### 1.2 How a dependency could break it

Merging a library that declares `INTERNET` in its own manifest would add the permission to the
release build without touching a line of application code. That is the realistic way this
guarantee fails, and it is why the gate is a build-artifact check rather than a source check.

To find the culprit if it ever happens:

```bash
./gradlew :app:dependencies --configuration releaseRuntimeClasspath
unzip -p <suspect>.aar AndroidManifest.xml | grep -i internet
```

## 2. What the app holds, and where

| data | at rest | why |
|---|---|---|
| message text | AES-GCM ciphertext in Room | see 2.1 |
| device key | Android Keystore, non-exportable | never in the database, never in source |
| display name | plaintext in `SharedPreferences` | it is a label, not a secret |
| device id | `Settings.Secure.ANDROID_ID`, hashed to `IT-%06X` | identifies the install, not the person |
| phone number | **never collected** | no account, no number, no server |

### 2.1 The database stores ciphertext, not plaintext

The user's own history is readable on their own device without a key lookup, so plaintext
would be simpler. It is stored encrypted anyway, for two reasons.

First, a plaintext history is a plaintext history **in backups and in memory dumps**, and
keeping encryption at rest a property of the app rather than of the storage layer means it
survives a change of database.

Second, and more concretely: it makes it structurally impossible to accidentally log or export
plaintext, because the only code path from a row to text goes through `EncryptionManager`. A
`Log.d("sending $text")` is a mistake that compiles either way; here it cannot be written at
all.

The cost is real and stated plainly: **opening the app needs the Keystore.** If the key is gone
— user cleared app data, or the app was reinstalled — the history is unreadable. `isReadable`
on a row tells the UI to say so directly rather than showing an empty chat that looks like
data loss.

## 3. Keys

`EncryptionManager` uses AES-GCM, **256-bit** keys (`KEY_SIZE_BITS = 256`), generated by
`KeyGenerator` with `KeyGenParameterSpec` under the `AndroidKeyStore` provider.

The GCM authentication tag is **128 bits** (`GCM_TAG_BITS = 128`), which is the maximum GCM
allows and the only value worth using: it is what makes a modified ciphertext fail to decrypt
rather than decrypt to garbage. A shorter tag is a strictly weaker forgery resistance, and
128 is what the platform's own provider defaults to.

**[ENFORCED]** the private key material never leaves the Keystore. There is no export path in
the code and no `getKey()` call that returns raw bytes to application memory. On devices with a
TEE or StrongBox the key may never be in the process at all.

### 3.1 Key generations, encoded in the alias

An alias carries its generation and creation time:

```
itantra_msg.g<N>.<createdAtMillis>
```

The active generation is the highest `N` among listed aliases. `rotate()` mints `N+1` and calls
`pruneRetired()`, which removes generations older than `RETIRED_KEY_GRACE_MS` = 7 days.

**Why the grace period.** A key cannot be deleted the instant it stops being used. A message
encrypted under generation 2 may still be *sent* — or delivered — after rotation, and deleting
generation 2 immediately would make those permanently undecryptable. Seven days is a
deliberate over-estimate rather than a measured figure: **NOT MEASURED** for this app, chosen
because it comfortably exceeds any plausible offline period in the intended use.

Generations are encoded in the alias rather than in a metadata file. A side file can be lost,
stale, or disagree with the keystore, and then the two disagree about which key is active —
which presents as every message failing to decrypt with no way to tell why. The alias is the
same store, so it cannot disagree with itself.

### 3.2 Never logged

**[BY DESIGN]** No key, IV, ciphertext fragment or plaintext is written to any log. Ciphertext
is excluded from the persisted `last_error` field as well as from `Log`, so the Settings >
Storage diagnostics screen cannot become an accidental exfiltration path.

`lastError` is documented as never containing a stack trace or a ciphertext fragment; see
`ERROR_HANDLING.md`.

## 4. Input validation

Every value that crosses the radio boundary is treated as hostile.

- **`EnvelopeCodec.decode`** returns `null` for 6 distinct rejection conditions, each checked
  before any attacker-sized allocation. Never throws — see `NETWORK_PROTOCOL.md` §2.2.
- **`Reassembler`** requires a 4-byte magic before trusting a length, resynchronises one byte
  at a time, and drops over-ceiling frames rather than buffering them.
- **Device and message ids** are length-checked and shape-checked at encode. A non-UUID
  `messageId` throws with a message naming the field, rather than being packed or truncated.
- **Payload size** is capped at 64 KB by the codec and again by the framing layer.

### 4.1 Replay and duplicates

**[ENFORCED]** A `messageId` already in the database is refused by a **unique index** on
`message_id`, not by an application-level check.

This matters because an application check is racy: two frames of the same message can arrive
close enough together to both pass a read-then-write. A unique constraint cannot be raced,
because the database is the thing serialising them. One message is stored, the second is
dropped, and the user sees one bubble — which is the correct outcome for a duplicate.

The cost is a stored `lastError` of constraint violation rather than a silent drop, so the
dedup path distinguishes "already have this" from "genuinely failed to store".

**Not implemented, and named rather than implied:** there is no timestamp-based replay window.
`messageId` uniqueness covers the realistic case (the same message arriving twice), but a peer
that can *generate* fresh ids at will is not constrained. Bluetooth bonding is what limits who
can reach the link at all.

## 5. Permissions

10 `uses-permission` entries in the release APK, each with a stated reason.

| permission | maxSdk | why |
|---|---|---|
| `BLUETOOTH` | 30 | pre-31 Bluetooth access |
| `BLUETOOTH_ADMIN` | 30 | pre-31 Bluetooth access |
| `BLUETOOTH_SCAN` | — | BLE discovery on API 31+ |
| `BLUETOOTH_CONNECT` | — | connect, and `BluetoothDevice.getName()` |
| `BLUETOOTH_ADVERTISE` | — | GATT peripheral role |
| `ACCESS_FINE_LOCATION` | 30 | BLE scan required location on API 23–30 |
| `ACCESS_COARSE_LOCATION` | 30 | as above |
| `NEARBY_WIFI_DEVICES` | 32 | declared for the Wi-Fi Direct path |
| `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | — | added by androidx, not by this app |

`INTERNET` is **absent**, and that absence is the point — see §1.

`NEARBY_WIFI_DEVICES` is declared but unused: Wi-Fi Direct has no implementation. It is
declared rather than removed because the brief lists it, and having the declaration means
adding the transport later is a code change rather than a manifest change. See
`LIMITATIONS.md` — a declared-but-unused permission is a reviewer question, so it is answered
here rather than left to be discovered.

**`ACCESS_FINE_LOCATION` is requested on API ≤ 30 and never above.** On API 31+ Bluetooth
permissions stand alone and location is not requested at all. A user on a modern phone is never
shown a location prompt by this app.

## 6. What this app does not protect against

Stated plainly, because a threat model that lists only wins is not a threat model.

| threat | status |
|---|---|
| Network interception | **[ENFORCED]** impossible — no `INTERNET`, no socket |
| Another app reading the database | OS sandbox, per-app private storage |
| Another app reading the Keystore key | Keystore is per-app; keys are non-exportable |
| A lost or unlocked phone | **not protected** — no app-level lock screen |
| A compromised OS or root | **not protected** — out of scope |
| Someone impersonating the display name over a bonded link | **not protected** — bonding authenticates the radio, not the user. See below. |
| Traffic analysis (who is talking to whom, when) | **not protected** — Bluetooth is radio-visible. Message content is encrypted; the fact of a conversation is not. |

### 6.1 Display names are not identities

A device id is derived from `Settings.Secure.ANDROID_ID` and the display name is typed by the
user. Neither is a cryptographic identity, and a message header carries both in the clear.

A peer on a bonded link can therefore claim any display name. What a receiver *can* rely on is
that the message came over a link with that MAC address, encrypted with a key that was never
transmitted. For the intended use — two people turning their phones towards each other and
reading the name on screen — that is the right trade. It would not be, for an adversary in the
room, and the app does not claim otherwise.

### 6.2 Device id entropy is 24 bits

`IT-%06X` is 24 bits, per the brief's specified format. That is ample for two people choosing
each other from a list, and too little for a dense environment — 24 bits is a birthday
collision in the low tens of thousands of installs in one area.

Mitigated by requiring explicit selection from a bonded/scan list rather than auto-connecting,
and recorded in `LIMITATIONS.md`. Widening the format is a wire change and was not done
unilaterally.

## 7. Checklist for a change

Before merging anything that touches crypto, storage or the manifest:

1. `bash scripts/check_offline.sh` — must exit 0. **Not exit 2.**
2. `./gradlew testDebugUnitTest` — must be green.
3. `aapt dump permissions app-release.apk` — no `INTERNET`, no unexpected additions.
4. If a dependency changed: re-read §1.2. A new library is the most likely way to break the
   central guarantee.
5. If a log statement was added: confirm it cannot receive plaintext, ciphertext or key material.
6. If an id field changed width: read `NETWORK_PROTOCOL.md` §2.1 first.
